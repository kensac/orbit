# The workspace

**Status: partly built.** Built: finding a workspace on both backends, snapshot reads (W1), snapshot writes, trash, uploads and the next turn told what the person changed (W3), snapshot change stream, file history and per-reply diffs (W6), review comments sent to the agent (W7), workspace audit, snapshot search, and an agent's box (sandboxd's `box` profile) with shell and direct Claude Code terminals over a WebSocket, plus Claude accounts in their own volumes. The rest is planned. The contract is in [api.md](api.md), Workspace, with every unbuilt part marked; the implementation items and their owners are in [WORKBOARD.md](WORKBOARD.md). The code is `internal/api/workspace.go` (reads and limits), `internal/api/workspace_search.go` (snapshot search), `internal/api/workspace_write.go` (writes), `internal/api/workspace_changes.go` (history, stream and run changes), `internal/api/workspace_review.go` and `internal/store/workspace_reviews.go` (review comments), `internal/api/terminals.go` (the box workspace and its terminals), `internal/store/workspaces.go` (snapshots and writes), `internal/store/workspace_changes.go` (the change index and run summaries), `internal/workspace` (snapshot indexes and diffs) and `internal/diff` (bounded line diffs).

The workspace is an IDE inside the orbit chat at `kanishksachdev.com/orbit` (kensac/personal-portfolio, `app/orbit`): a file explorer, an editor, several terminals (one of them can be Claude Code's own interactive TUI, "Claude Code (direct)"), and a diff view whose line comments go to the agent. orbit serves only the API. The portfolio is the only surface: no subdomain, no orbit-hosted page, no desktop or editor integration.

## One shell, not panels

The chat, the workspace, the editor, terminals, diffs, agents and memory are one application. Every portfolio PR that adds or changes a panel meets these, and its description says how:

- **One layout and navigation.** One frame: a rail (conversations, agents, memory, explorer, search), a main area of tabs (thread, file, diff, terminal, agent, memory entry), and the chat beside it. Panels are tabs and docks inside it, never separate pages with their own chrome. A tab survives switching conversations and is restored on reload.
- **One command palette.** A single registry: each panel registers its commands (open file, new terminal, Claude Code (direct), diff vs base, send review, approve action, switch agent, search). One shortcut opens it everywhere; no panel has a palette of its own.
- **One set of design tokens.** Colours, type, spacing, radii and motion come from the portfolio's tokens, light and dark. The editor, xterm and diff themes are derived from those tokens, not shipped with their own palettes.
- **One state store and one opener.** Everything is addressed by orbit's ids: `conversation_id`, `workspace_id` with a path and line, `run_id`, `terminal_id`, `action_id`, a memory entry's id. One `open(ref)` places a ref in the main area, and deep links (`/orbit/c/<conversation>?open=<ref>`) are the same refs. So a path in a reply opens in the same editor tab the explorer opens, a reply's "files changed" opens its diff in the diff tab, an approval in a terminal's flow is the same action card as in the thread, and an edit in the editor is the same buffer the diff view shows.
- **No duplicate fetches.** Panels share the store's caches and streams: one thread stream per conversation, one change stream per workspace, one socket per attached terminal per tab.

The API supports this by naming everything the same way: a conversation carries its `workspace_id`, a run item carries its `changes` summary, and a path in a run's journal (`tool_call` summaries, `diff` items) is relative to the run's directory, which for a chat agent is the workspace's `cwd`.

## Where files and shells live

A **workspace** is one tree of files a person and an agent share, behind one API. It has a backend:

| backend | where | what works | when |
|---|---|---|---|
| `snapshot` | the conversation's newest workspace snapshot (`workspaces` rows, written after every chat run) | read, write (a new snapshot), trash, upload, download, the change stream, per-reply diffs, history. No terminals, no git commands. | first: every chat conversation has one |
| `box` | the agent's shared workstation: a persistent container on hetzner or oci, made by sandboxd | human terminals and git; model chat processes never run in this box | once the workstation exists |

A client reads `capabilities` and never the backend name to decide what to show, so moving an agent from snapshots to a box changes no route and no shape. `GET /conversations/{id}/workspace` remains the conversation's snapshot. A workstation chat restores that snapshot into a separate persistent container dedicated to the conversation, then archives its workspace back after each turn. The shared agent box is reserved for human terminals and git, so conversations do not share a model process, account volume or HOME through that box.

**Snapshot backend.** Reads come from the stored tar, so they work whichever host ran the conversation and whether or not its sandbox is up. A write stores a new snapshot (author: the person) and the next run restores it; a live session process is not reused after one (its sandbox holds the old copy), so the session resumes in a new process started from the person's version. A write while a run of the conversation is running is refused (`busy`), since the run's own snapshot would follow it; an advisory lock per conversation, exclusive for the write and shared for the run's restore, makes the check and the restore exclusive of each other. orbit never runs git over a snapshot: a model-written `.git/config` can name commands (`core.fsmonitor`, hooks) that git would run on orbit's host. Git therefore exists only in the box.

**The box.** One shared container per agent (`orbit-box-<agent>`), created by sandboxd's `box` profile (`internal/sandboxd/box.go`) from the workstation image (`ORBIT_SANDBOX_BOX_IMAGE`): named volumes for `/work` and `/home/agent` that outlive the container, no lifetime timer, restart `unless-stopped`, the open egress proxy, and uid 10001 for every process. Human terminals and git use this box; model chat processes do not. It still mounts configured account volumes for direct Claude terminals, so every process in it can read those mounted credentials. Its runtime is runc today and `ORBIT_SANDBOX_BOX_RUNTIME=runsc` moves it to gVisor. Unlike a build sandbox it keeps docker's default capabilities (less `MKNOD` and `NET_RAW`), a writable root and no `no-new-privileges`, so the image's sudo works (docs/agents/security.md, Boxes and terminals). A stopped box is recreated on the current image pin when it is next needed; a running one keeps its image. Its image is multi-arch (amd64 for hetzner, arm64 for oci) and carries a laptop's tools: git, gh, jq, ripgrep, fd, curl, make, node, python, go, tmux, the pinned `claude` CLI, and docker (a daemon inside the box is a later tier of the profile). PID 1 is `orbit box`, a helper in the image that serves file operations (through `os.Root`, so nothing escapes the tree), git, tmux and an inotify watcher over the attach channel. Its `/work` and `/home` are stored as snapshots after every agent turn and at most every 10 minutes while a person edits, so the box can be rebuilt on either host and history survives it. An agent's shared box lives on one host at a time; moving it is a snapshot and a restore.

**The chat box.** A workstation chat has one persistent sandboxd container per conversation, named from a hash of the conversation ID. It uses the workstation image and egress proxy, but has no account mounts and cannot use the shared box's terminal or account routes. Each turn restores the conversation's workspace and HOME snapshots into its own volumes and archives changes back afterward. sandboxd seals the one backend credential into a proxy grant bound to that container, address and run; after 55 minutes the runner kills the CLI process even during a turn, while the container and workspace remain for a later run. The raw backend credential never enters the chat container.

## Files

Paths are relative to the workspace root, POSIX, clean, inside the tree (symlinks are shown, never followed out of it). A file's `version` is `sha256:<hex>` of its bytes, sent as its `ETag`.

- **Tree** is lazy: one directory per request, with `has_children` on directories, `ignored` from `.gitignore` and, in a box, each entry's git status. The explorer loads a directory when it opens and keeps it current from the change stream.
- **Read** returns text for the editor up to 2 MiB; a larger file or a binary one (a NUL in the first 8000 bytes, as git decides, or invalid UTF-8) returns its stat and a `reason` instead, and the editor offers download or, for raster images, a preview.
- **Write** needs `If-Match` with the version the editor read, or `If-None-Match: *` to create. A mismatch is `412` with the current version, so two devices never silently overwrite each other; the editor shows a merge.
- **Delete is a move to the trash** (`.orbit/trash/` in a box; on the snapshot backend the earlier snapshot keeps the content). Nothing is deleted: the trash has no empty operation, and every item can be restored. Rename never overwrites.
- **Upload and download**: multipart up to 64 MiB a file, a signed URL above that (as conversation uploads), a directory downloads as a tar.gz.
- **Search** is code over the files as they are (or at a past version): literal or RE2, line by line, columns in UTF-16 units for the editor, results bounded in count, preview and time.
- **The change stream** (SSE) tells the explorer and open editors what changed and who changed it (the person, a run, a terminal); a lost cursor or a watcher overflow sends `resync`, and the client re-reads what it shows.

## Terminals

A terminal is a tmux session in the box: it survives the browser closing, a deploy of orbit, and several devices attaching at once (tmux sizes the window to the most recent active client). tmux over dtach because it gives scrollback to replay and per-client sizing; dtach gives neither.

- **Presets.** `shell` (`tmux new-session -A -s <session>`, a shell in `cwd`) and `claude` (`tmux new-session -A -s <session> claude`): the pinned `claude` CLI in its interactive TUI, in `cwd`, with the box's HOME (so its sessions and settings persist) and the subscription credential in that terminal's environment (the attaching client carries it, tmux's `update-environment` copies it into the session). The session is the terminal's own, `<preset>-<12 hex of its id>`, so several Claude Code terminals can run at once. sandboxd builds the argv from the preset; a request never carries one. Options (resume a session, continue, model) are planned as a fixed list, never an argv. This is "Claude Code (direct)": the person driving Claude Code themselves, not an orbit run, so orbit records its lifecycle, not its turns.
- **Attach** replays up to 10,000 tmux scrollback lines (including terminal attributes, capped at 4 MiB) before forwarding the attached client stream. A socket closing hangs up only its own tmux client, so the session and other devices carry on. The socket protocol is binary frames for terminal bytes and JSON text frames for control (resize, exit, ping); api.md has it exactly. A standalone resize route changes the tmux window for clients that cannot send an in-band resize.
- **Toolset and GitHub.** Every terminal has the full toolset above. The box's `gh` wrapper and git credential helper use an installation token scoped to its configured repositories; see [GitHub in the box](#github-in-the-box). A person at a terminal may `git commit` and `git push` and use `gh` with write access: direct mode holds GitHub write credentials, and that exposure is accepted for now.

### Accounts

A person can keep several Claude accounts in a box, as `claude` on a laptop keeps them with `CLAUDE_CONFIG_DIR`: one directory per account, `/home/agent/.claude-accounts/<slot>`, each on its own named volume (`orbit-box-<agent>-acct-<slot>`), mounted into the home. A terminal under an account runs with `CLAUDE_CONFIG_DIR` set to that directory in its tmux session, and with the subscription token (`CLAUDE_CODE_OAUTH_TOKEN`) and every `ANTHROPIC_` variable removed from its command's environment and the token marked removed in the session (so a window opened in it later lacks it too), so the account's own login is the one used. Agent runs do not use these account directories. Sandboxed runs reach the backend through the credential proxy; a person's direct terminal keeps its own login.

- **Why a full login.** A setup token only carries `user:inference`; claude.ai connectors need the scopes of a full `claude auth login`, which works headless: it prints a URL and the person pastes back the code. Adding an account opens a terminal running exactly that under the new directory. The login's refresh token rotates on every refresh, so a login is never copied between directories: each account logs in once, in its own.
- **Shared and private.** `settings.json`, `CLAUDE.md`, `skills`, `commands` and `agents` are symlinks into the shared profile, `~/.claude`, written when the account is made and again before each of its terminals starts (an entry the CLI replaced with a file of its own is left alone). Everything else in the directory, credentials, `.claude.json` (the account's identity and user MCP servers), sessions and history, is the account's own.
- **Mounting.** A container's mounts are fixed when it is created, so a running box gains a new account's volume only by being recreated, which ends every session in it (the terminals are recorded `box_restarted`); the API asks before doing that while terminals run. A stopped box is recreated with every account it had and the new one, and a recreate never unmounts one.
- **What orbit knows.** Email, organization, subscription type, rate-limit tier and the access and refresh tokens' expiries, read by a fixed script that selects those fields of the account's files in the box. Never a token: those exist only in the account's volume.
- **Usage.** The box image's status line (`orbit-statusline`, set for every Claude Code in the box by `/etc/claude-code/managed-settings.json`) writes the `rate_limits` the CLI hands it to `$CLAUDE_CONFIG_DIR/.orbit/usage.json`, then prints the person's own line (`~/.claude/statusline-command`, given the same input) or a short default; managed settings win over a `statusLine` in the shared settings, so that file is where a person's own line goes. orbit reads the record with the account. It exists only once an interactive Claude Code has run under the account, so `ORBIT_ACCOUNT_USAGE_POLL` (off by default) can also poll the undocumented `/api/oauth/usage` for each logged-in account of a running box, from inside the box with the account's access token. The poll never refreshes a token (a refresh rotates the refresh token under the CLI that owns it), so an account no Claude Code has used for hours answers 401 until one runs.

### Connectors and MCP

Each account has its own MCP servers and claude.ai connectors, as each has its own `.claude.json` and login; orbit adds three things.

- **A list.** `claude mcp list` run as the account (`GET .../accounts/{aid}/mcp`), parsed into name, transport and status, so the portfolio shows which connectors need a login. Raw targets, command arguments and provider error details are omitted because they may contain credentials.
- **Logging in to one.** A connector or an OAuth HTTP server is logged in to per account by `claude mcp login --no-browser <server>` in an `mcp-login` terminal: it prints a URL and takes the pasted redirect back, as `claude auth login` does. Its tokens land in the account's directory, like its login.
- **Servers orbit manages.** `box.mcp_servers` in `orbit.yaml` (docs/agents/spec-reference.md, `box`) are added to every mounted account with `claude mcp add-json -s user`, within a minute of a box running or the configuration changing (`internal/boxkeep`); one orbit added is removed when it leaves the map, and what orbit added is recorded in the account's `.orbit/mcp-managed.json`, so a server of another name that the person added is never touched. Credential-bearing fields, secret-like arguments, URL credentials, queries and fragments are refused; a server needing auth uses OAuth, logged in to per account as above.
- **Skills.** orbit's skills library (every active skill, docs/api.md, Skills) is written into the shared profile, `~/.claude/skills/<name>/`, which every account links, within a minute of a box running and whenever a skill changes; a skill orbit put there and later retired is removed (`~/.claude/skills/.orbit-managed` lists them), and a directory of the same name that is the person's own is left alone and that skill skipped.

### GitHub in the box

orbit keeps a GitHub App installation token in every running box at `/run/orbit/gh-token` (the box user's, 0600, in a 0700 directory), where the image's `gh` wrapper exports it as `GH_TOKEN` and the system git credential helper answers `https://github.com` with it. `internal/boxkeep` writes it within a minute of a box starting or being recreated and again every 45 minutes, a token at most 10 minutes old, so a box always holds one with time left (installation tokens last an hour; each is left to expire, never revoked early, since a box written a minute before still holds the previous one). The token is in orbit's memory and the box's file only, never in orbit's database, a log or git.

- **Which repositories.** `github.box.repositories` when it names them; otherwise every repository of the App's installation on `github.box.owner` that `github.box.exclude` does not match, by default every one but the homelab host repositories (`*/*-config`). Its permissions are `github.box.permissions`, by default contents and pull requests write, checks and statuses read, never workflows (docs/agents/spec-reference.md, `github.box`).
- **His own login instead.** With `github.box.token: false` orbit writes none and removes the one it wrote from each running box, so `gh auth login` (and `gh auth setup-git`) in a terminal is what gh and git use; with the file present the wrappers prefer it.
- **Who can read it.** Every process in the box, the person's terminals and, once agent turns run there (W10), a model's: the exposure direct mode accepts, closed later by the planned credential proxy. Unattended agents still push only through `workspace:push`, with a token they never see.

### Transport: through the proxy, or straight to orbit

The portfolio reaches orbit through a server-side proxy on Vercel that forwards the authentik token, so the browser never holds it. A terminal needs a bidirectional, long-lived stream, and Vercel functions do not accept a WebSocket upgrade and cap how long a response may stream. The spike on Vercel, Cloudflare and traefik has not reported at the time of writing, so the contract supports both paths and the client picks:

| | direct: WebSocket to `orbit.kanishksachdev.com` | through the proxy: SSE out, POST in |
|---|---|---|
| how | the proxy asks orbit for an attach ticket (authentik token, server side); the browser opens `wss://orbit.kanishksachdev.com/api/v1/terminals/{id}/ws` offering the subprotocols `orbit.terminal.v1` and `orbit.ticket.<ticket>`, so the ticket is in a header rather than the URL (`?ticket=` is accepted as a fallback). The ticket is single-use, names one terminal and one person, is bound to the Origin it was minted for (or, minted server side without one, to the portfolio's allowed origins), and expires in 30 s; the browser never sees the authentik token. | output as SSE (`/terminals/{id}/output`, resumable with `Last-Event-ID`), each keystroke batch a `POST /terminals/{id}/input`, both through the proxy |
| latency | one round trip to hetzner per keystroke | a Vercel invocation per input batch, plus its cold starts |
| limits | Cloudflare closes a WebSocket idle for 100 s, so the client pings every 10 s, the server answers at once and pings every 15 s; traefik passes upgrades as is | the function's streaming cap ends the SSE every few minutes and the client resumes; each input is a billed invocation |
| exposure | orbit's public listener takes the socket, so it checks `Origin` against the portfolio's origin (no cross-site socket) and rate-limits tickets | nothing new is exposed |

Built: direct. WebSockets pass through Cloudflare and traefik's `/api/v1` router (no forward-auth). The proxied path stays the planned fallback, and so does `Authorization: Bearer` on the socket for a proxy that can carry a WebSocket.

## Git

In a box, for every repository under the workspace (a directory with `.git`, up to three levels deep): status, diff of the worktree against `HEAD` or any base (a ref, or `merge-base:<ref>` for "what this branch changed"), log and history of a file, a file at a revision, branches. Diffs come back structured (files, hunks, lines with numbers) so the diff view and its comments anchor to exact lines, with caps and a truncated flag.

- **Per-reply diff.** What one reply changed: on the snapshot backend, the snapshot before the run against the one after; in a box, orbit's checkpoints (a tree written into a separate git directory under `.orbit/` at the start and end of every turn, not touching the repository's index or history). Every run item in a thread carries a `changes` summary; the diff view opens `GET /runs/{id}/changes`.
- **Line comments to the agent** work as a ticket's review comments do (tickets.md, Review comments): drafts on a path and line range, anchored to a run's change, a git diff or the worktree; edits are new versions; sending the review writes one message to the conversation, formatted by code with each comment's file, lines, the quoted code and the body, and wakes the agent.
- **Commits and pushes, two paths.**
  - **Direct, by the person**: from a terminal with git and gh, or the workspace's commit and push routes, which run git in the box as the person with the terminal's GitHub credential. Nothing is approved; it is the person's own action, recorded in the workspace's events.
  - **Unattended, by an agent**: the box's agent turns are not given a GitHub token (though, in the box, they could read the one gh and git use, above). An agent proposes `workspace:push` (the repository, the branch, the commit range); orbit's executor reads the commits out of the box as a bundle, applies the diff policy (tickets.md) and pushes with an App token for one repository from `github.repositories`, to a branch that is not protected. The rule decides whether a person approves first. Merges stay `github:merge`.

## Auth, scope and limits

- **Auth** is the authentik JWT as for every route, checked by orbit. The socket takes a ticket minted with one. Writes, trash, uploads, terminals and git writes also require `ORBIT_WORKSPACE_GROUP` (default `ORBIT_OIDC_GROUP`), so the shell can be narrowed to fewer people than the chat (built so far: the default, which every API token already meets; a narrower group is planned).
- **Scope.** A workspace belongs to one conversation (snapshot) or one agent (box), and every route checks the workspace exists and the ref it names belongs to it. An agent's runs reach only their own agent's box; no agent is given the workspace API or another agent's box.
- **Limits** (per person per workspace unless said): reads 100/s, writes 20/s, 8 running terminals per workspace, 8 clients per terminal, 10 attach tickets a minute; editor read 2 MiB, write 8 MiB, upload 64 MiB a file (signed URL to 1 GiB; on the snapshot backend the whole tree is at most 256 MiB, sandboxd's tar limit), tree 2000 entries a page, diffs 300 files, 5000 lines a file, 10 MiB in all. Over a rate is `429` with `Retry-After`. A socket client that takes no output for 30 s is closed (4008) and reattaches. Built so far: the terminal count, the clients per terminal (counted per instance) and the ticket rate.
- **Audit.** Every workspace operation is a `workspace_events` row (append-only, as the journal is): the operation, path, versions before and after, bytes, person, terminal, request id. Terminal lifecycle is recorded (today in the `terminals` rows: created, attached, ended, by whom); terminal input never is (it carries passwords). The next agent turn in the conversation is told, by code, which files the person changed since its last turn.

## What a compromised model can do here

A chat agent in a workstation sandbox can already run any command with open egress. The box adds: a person's terminals in the same container, so a model's process can read a terminal's environment, the GitHub credential included, and act as the person on GitHub. That is accepted for now and closed by the planned credential proxy. The model still cannot reach orbit's secrets, the App key, another agent's box, or the host. Snapshots and the trash keep every file it overwrites or removes.
